## First server foundation

The development branch adds a dedicated MariaDB 10.11+ schema for users, hashed invitations, revocable sessions and one conversation per client. A migration ledger detects source drift and interrupted DDL, serializes migrators with a database-scoped lock and requires explicit recovery. See [database configuration, migration and recovery](docs/DATABASE.md).

`npm run db:migrate -- status` is read-only apart from connection session settings and a temporary advisory lock; `npm run db:migrate -- up` initializes/applies the reviewed schema in an explicitly confirmed dedicated database. No migration runs on server startup. CI uses disposable, synthetic MariaDB 10.11 and 11.4 databases.

Administrator sign-in now combines an exact password with a fresh authenticator code or a single-use recovery code. Sessions use a Secure/HttpOnly host cookie, database revocation, strict Origin/CSRF checks and persistent rate limits. Both administrator and client sessions last 180 rolling days without an idle timeout in the active `photos-notify-recovery` transition profile. Revocation, credential changes and cookie deletion can still end a session; concurrent household-device acceptance remains pending. See [client-session and notification-opening policy](docs/notification-opening.md). Administrators can review and revoke their individual device sessions; signing out all devices requires confirmation. See [stage 0.30 policy and remaining acceptance](docs/durable-admin-sessions.md). The one-time private setup CLI creates no default credentials. See [setup and operational limits](docs/auth-admin.md). Invitations, atomic registration and encrypted verification mail jobs are implemented. Verified email permits a limited client session. Active access follows the configured admission policy; the current service requires a consumed invitation, verified email and explicit approval by Jessie. No API converts an age declaration into independent verification. The separately enabled text chat checks live conversation ownership, session generation and client gates inside each database transaction. `/messages` gives an active client one conversation; `/admin/messages` gives the assigned administrator a private inbox. An additional media flag/key/private directory enables photo messages, a private gallery and reusable owner assets.

`JESSIEMESSAGE_ENABLE_CRM=1` requires chat and a separate `JESSIEMESSAGE_CRM_KEY`; media is optional. The key must differ from MFA, mail, message and any configured media key. Three additional reviewed migrations (`0018`–`0020`) supply private profiles, labels and memberships. Only a current assigned administrator can read or edit a client file: up to 8,000 characters of encrypted notes, 32 labels and a private reminder date. Labels allow 100 tags and 100 groups per administrator. Search and tag/group, access, unread and reminder filters apply on the server. Dates do not trigger notifications; groups do not create shared rooms. Individual broadcasts are separately enabled; Device Web Push is separately enabled by the notifications profile; see the 0.31 validation record above.

`JESSIEMESSAGE_ENABLE_CLIENT_RECOVERY=1` requires enabled access and its mail configuration, independently of chat, media or CRM. It reuses the private mail key with cryptographically distinct verification/reset purposes. Two reviewed migrations (`0021`–`0022`), already present in schema 30, provide hashed reset challenges and a separate encrypted outbox. An eligible email-verified pending or active client receives a single-use, 30-minute link. A successful reset atomically changes the password and revokes that client’s sessions on both origins; other clients and the administrator are unaffected. It grants no session or access. Opening the link consumes nothing. See [configuration, transaction guarantees and remaining release work](docs/client-recovery.md).

`JESSIEMESSAGE_ENABLE_BROADCAST=1` requires the CRM and therefore active chat/access configuration. Three new migrations (`0023`–`0025`) store client preferences, encrypted immutable campaigns and durable recipients. Preferences default to false and only the client can change them. The worker reuses the message key with a separate cryptographic purpose and shares normal chat send quotas. A confirmed campaign continues after logout, while current administrator status/MFA changes, recipient opt-out, expiry or revocation prevent further delivery. See [configuration, guarantees and release limits](docs/targeted-broadcasts.md).
